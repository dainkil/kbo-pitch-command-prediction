## 1. 배경과 문제 — 왜 해결할 가치가 있었는가

**과제.** KBO 투구 데이터에서 투수가 의도한 코스에 공을 넣었는지(제구)를 3등급 확률로 예측한다. 제출은 예측값이 아니라 **코드 zip**(script.py + model/)이고, 채점 서버(6 vCPU·28GB·인터넷 차단)에서 10분 안에 추론해야 하며, 평가 행끼리 서로 참조하는 것(test 집계·순위·분포 보정)은 실격이다. 즉 "잘 맞히는 모델"이 아니라 **"규정 안에서, 배포 환경에서, 평가식이 보상하는 것"**을 만드는 문제였다.

**모델링 문제의 재정의 — 점수는 어디서 나는가.** 첫 EDA에서 평가식을 분해했다. Brier 0.01 = Score 0.35, τ 0.01 = Score 0.15 이므로 가중치(0.7 : 0.3)만 보면 Pitch 가 중요해 보이지만, **움직일 수 있는 폭**이 다르다.

- Pitch: 상수 prior 69.71 → 볼카운트 표 69.85 → 투수 EB 69.97 → LightGBM 70.0. 대회 상위권도 70.18~70.25. **폭 0.5, 포화.**
- Player: τ 0 → 0.3 이면 +4.5점. 상황 정보만으로 순위를 매기면 τ −0.23(역상관). **점수 차이의 전부.**

그래서 이 대회를 "3-class 확률 예측"이 아니라 **"Brier 를 잃지 않으면서 투수 순위(τ)를 맞히는 문제"**로 재정의했고, 이후 모든 결정은 이 축 위에서 내렸다.

**기대치 설정 — 상한이 있다.** 투수 간 참 실력 sd 1.76 ≈ 투구 523개 평균의 표준오차 1.60. 신호대잡음이 1:1 이라 **완벽한 실력을 알아도 τ 0.59~0.65** 가 상한이다. "Player 100" 을 쫓지 않고, 잡음 아래로 내려가지 않는 순위 신호만 골라내는 것을 목표로 잡았다.

## 2. 데이터 — 출처·규모·전처리와 라벨링 이슈

**출처와 규모.** 주최 제공(외부 데이터 금지). `train.csv` 1,474,868행 × 29열(시즌·이닝·볼카운트·주자·점수차·승리기대·LI·투수/타자 ID·손·팀·game_type R/F), `train_outcomes.csv`(등급 라벨·투구 위치·반대투구·스트/볼·결과·구종 = **사후정보**), `train_trackman.csv` 물리량 31열(부분 연결). `test.csv` 는 더미 5행이고 실제 평가 218,992행은 비공개.

**라벨링·전처리 이슈 4가지와 결정.**

1. **라벨 결측 17.16%(253,122행) = Unlabeled, Failure 아님.** 규정대로 지도학습에서 제외했다. 대신 결측 행도 "이력"으로는 쓸 수 있어, (스트/볼·결과·구종·반대투구·카운트) 조합 평균으로 채운 **대리등급(pgr)** 표를 만들어 투수 이력 집계에만 넣었다(팀 seongmin 이 조건부 버전 PGR2 로 고도화).
2. **라벨 규칙 100% 재현.** 좌표(|x|, y)로 Heart/Shadow 경계를 복원해 라벨이 결정론적임을 확인 → 사후정보는 "과거 이력 집계"로만 쓰고, 평가 행에는 절대 들어갈 수 없음을 팀 규칙으로 못 박았다.
3. **평가셋의 정체.** 218,992 ≈ 2024 라벨 확정 행 218,836 → **평가셋 = 2025 라벨 확정 투구만**. 50구+ 투수 321명이 평가 투구의 99.4% 를 던지고, 그중 신인(이력 0) 60명(19%), 이력 1,000구 미만 154명. Player 는 이 321명의 순위 문제다.
4. **2023 퓨처스(F) 체제변화 — 가장 중요한 발견.** F 경기 반대투구 기록률이 2022 4.9% → 2023 30% → 2024 29% (같은 투수 70명 기준, 신인 유입 아님). 전 시즌 평균 상황표를 쓰면 τ −0.23, 최근 1시즌만 쓰면 +0.27 로 **부호가 뒤집힌다**. 게다가 2025 는 전 구장 ABS·Trackman 첫 해라 **오프라인에서 관측할 수 없는 체제**다. 이것이 뒤에 나오는 "폴드가 Player 를 못 맞춘다"의 원인이다.

**전처리 결정.** 라벨 행만 학습(옛 시즌은 이력 재료로만) · 이력 피처는 LOSO(leave-one-season-out)로 만들어 인샘플 오염 제거(+1.80 Score) · 채점 서버(py3.11 / numpy 1.26.4)와 개발 서버(numpy 2) 가 달라 pickle 금지, 표는 npz+json·모델은 LightGBM txt 로 저장.

## 3. 접근 방법 — 기준 모델, 실험 설계, 핵심 ADR

### 3-1. 기준 모델 사다리 (무엇과 비교했는가)

| 모형 | 오프라인 2024 폴드 Score (τ) | 의미 |
|---|---|---|
| 상수 prior | 63.79 (0) | 바닥 |
| 볼카운트×game_type 표 (전 시즌) | 60.51 (−0.226) | 상황은 실력과 **역상관** — 좋은 투수가 유리한 카운트를 만든다 |
| 투수 클래스비율 EB(α 200) | 66.91 (+0.206) | 이력만으로 τ 0.2 |
| LightGBM 상황+이력 (season 없음) | 66.98 (+0.201) | GBDT 가 EB 와 동급 |
| **LightGBM + `season` 열** | **68.81 (+0.321)** | 체제 인식 한 열로 +1.8 |
| 오라클(평가시즌 투수 클래스비율) | 78.96 (1.0) | 도달 불가 상한 |

LB 기준선: 주최 베이스라인(RandomForest + 투수 EB) **68.527 / 70.115 / 64.595**. 내 첫 제출 d4(LightGBM 69피처 5시드 단독)는 **67.198 / 70.206 / 60.179** — Pitch 는 대회 최고급인데 Player 가 베이스라인보다 4.4 낮았다. "GBDT 는 Brier 를 최소화하느라 투수 순위를 상황 순위로 덮어쓴다"는 것이 첫 진단이었다.

### 3-2. 실험 설계 (변수를 어떻게 나눴는가)

- **예측을 두 축으로 분해**: `p = anchor_proj(q, t)`. q = 행 확률(LightGBM, Pitch 담당), t = 투수 목표 제구점수(EB + 행 항 + 오프셋, Player 담당). 사영 `p = q + (t − q·G)/(G·v)·v` 는 "100p_S + 30p_H = t, Σp = 1" 제약 아래 q 에 가장 가까운 해라서, **Player = τ(t) 가 정확히 성립**한다. 한 실험은 한 축만 바꾼다 — Player 후보는 투수 단위 항으로, Pitch 후보는 t 를 고정하고 q 만.
- **시간 검증**: 평가면 2024, 학습 ≤2023 의 expanding window. 2023 폴드는 체제변화가 평가시즌 안에서 일어나 어떤 방법도 못 맞추므로 제외.
- **검증 규율(팀 합의)**: Pitch 는 폴드 → LB 이관율 0.5~1.0 으로 신뢰. **Player 는 폴드 부호가 LB 와 0/7 일치** → 폴드 값은 참고만, 판정은 LB 1회 탐침. 하루 100회 한도를 "가설 한 개 = 제출 한 개" 로 썼다.
- **게이트 자동화**: 빌드 스크립트가 (a) 행 독립 — 30k 부분집합·단일행·역순 예측 비트 비교(<1e-10), (b) 확률 합·범위, (c) 2024 라벨행 재현 점수, (d) 기준 번들 대비 투수 평균점수 최대차를 출력. 팀에서 실제로 학습/추론 불일치(L8, τ −0.08)가 났던 뒤라 "게이트 안 통과 = 제출 안 함"을 원칙으로.

### 3-3. 핵심 ADR (상황 → 대안 → 결정과 근거 → 결과)

**ADR-1. GBDT 단독 → q/t anchor 분리 구조** (d4 → d5, 09-19 낮)
상황: d4 는 Pitch 70.21 인데 Player 60.18. 대안: (a) GBDT 에 순위 신호를 ε 만큼 섞기, (b) 사후 순위 재배치, (c) 투수 목표값을 따로 두고 GBDT 는 등급 배분만. (a)는 ε 튜닝마다 Brier 를 잃고, (b)는 "평가 행 간 참조" 규정 리스크. **(c) 채택.** 결과: d5 **68.627 / 70.166 / 65.036** — Pitch −0.04 에 Player +4.9. 이후 팀 전체 구조가 이 분리 위에서 움직였다.

**ADR-2. 체제 인식은 `season` 열 하나로** (EDA 13/19)
상황: F 체제변화를 어떻게 모델에 넣을까. 대안: regime 플래그(≥2023), season×game_type 표, season 열 그대로. 폴드에서 season 열 τ .321 > 플래그 .289 > 표 — 연도별 미세 변화까지 트리가 쓴다. 최근 2시즌만 학습해도 68.81 로 동일 → 옛 시즌은 이력 재료로만. **season 열 채택**, 추론 시 2025 는 "≥2024 분기"로 떨어져 최신 체제 유지와 동치.

**ADR-3. 하이브리드 — 팀 목표 t + 내 q** (d20, 09-19 밤)
상황: 종민의 목표값 파이프라인(L87)이 Player 68.30 으로 팀 최고, 내 GBDT 는 Pitch 70.18 로 최고. 대안: 각자 계속 vs 부품 결합. 종민 번들의 t 를 그대로 가져오고 등급 배분만 내 5시드 q 로 바꾼 하이브리드를 빌드 → 2024 가짜 test 에서 행별 점수가 L87 과 2e-14 동일. 결과: d20 **69.6032 / 70.1623 / 68.2985** — **Player 10자리 동일, Pitch +0.044.** 이후 "목표값은 종민 최신, q 는 dain" 이 팀의 결합 표준이 됐다.

**ADR-4. 볼카운트 행 항** (d21 → d22, 09-19 밤) — 가장 큰 단일 기여
상황: 투수 목표 t 는 투수 평균이라 "이 행이 0-2 카운트인지 3-0 인지"를 모른다. 투수 잔차를 행 상태 z(볼·스트·주자·득점·아웃)에 릿지 회귀 → β balls −5.74 · strikes +2.51 · runners −1.43 · run_total −0.54 · outs +1.32, 이력 가중 w_p = 2000/(n+2000). 쟁점: 팀에서 한 번 "지표 조작"으로 폐기됐던 축. 규정 문구("자기 행의 열 + 학습으로 만든 상수"만 허용)로 다시 판단하니 γ_F·anchor 와 같은 등급의 절충이라 **재추진.** 세기 곡선: scale 1.0(d21) Player +0.54 → **scale 0.5(d22) +1.08**, **69.8864 / 70.1034 / 69.3802 (당시 팀 최고)**. 종민 파이프라인에 표준 부품으로 이식돼 L110→L164→L236 계보를 탔다.

**ADR-5. 오프라인 Player 검증 폐기 → LB 이웃 규칙** (09-19 밤 ~ 09-20)
상황: d6·d7(위치 이력 주입)이 3폴드 ✓ 인데 LB Player −0.16 / −0.59. skill prior·soft 재라벨(폴드 τ +.06~.10)도 같은 냄새. 원인 분석: 폴드에서 뒤집힌 개입은 전부 **"F 비중 높은 소이력 투수"** 에 이득이 집중 — 2023~24 폴드는 그들을 +3~5 과대예측하고 2025 는 반대. **결정: Player 후보는 LB 에서 이미 양수인 가족(행 항·강수축·작은 직교 잔차)에서만, 새 축은 단독 탐침 1회.** 이 규칙이 마지막 날 d28·d30b·d36e 세 번의 실패를 각 1회로 막았다.

**ADR-6. Player 불변 q 앙상블 + 온도 후보정** (d37 → dFING2, 09-20 06:00~09:42)
상황: 마감 4시간 전, 팀 최고 FIN_G(70.3072). Player 를 건드리는 모든 후보가 LB 에서 음수. 사영 구조의 성질 — **q 를 바꿔도 t 가 고정이면 투수 평균점수가 비트 단위로 불변** — 을 이용해 하방 위험 0 인 Pitch 회수를 택했다. q = 0.5·dain 5시드 + 0.5·종민 5시드, 온도 T 는 ≤2023 홀드아웃의 2024 표본외에서 anchored Brier 최소화(T .85~.9 → +0.016; 클래스 편향항 +0.026 은 체제 의존이라 제외). 게이트: 행 독립 1.1e-16, 투수 평균점수 최대차 7e-15. 결과: **dFING2 70.3140 / 70.1038 / 70.8044 — Pitch +0.010, Player 비트 동일.** 인샘플 +0.049 가 LB +0.010 으로 이관(dain q 의 인샘플 과장 ~5배, 예상 범위).

### 3-4. 기술 선택 이유 (짧게)
- **LightGBM**: 1.4M 표형, 12스레드로 시드당 50초. 확률이 이미 캘리브레이션됨(T=1 최적). txt 저장으로 numpy 버전 독립. TabPFN(투수×시즌 잔차)·스택·저랭크는 폴드 양수였지만 LB 미검증이거나 게이트(단일행 비트 동일) 실패로 제외.
- **EB 수축**: prior 를 배치셀(li×이닝×점수차 60셀, "감독의 기용이 실력을 드러낸다")로 두고, 수축 강도는 MSE 최적보다 **3.7배 강한 α 1,800~2,400** 이 LB 최적(600 으로 풀면 Player −1.09). 이력 정밀화보다 **강한 수축 + 평가행 구성 보정**이 정답이라는 경험칙.
- **직교 잔차**: 새 순위 신호는 기존 목표값·log n·F 비중에 대해 직교화한 뒤 총 sd 0.5 까지만. 그 이상은 LB 하락.

| d5 | anchor 분리 (ADR-1) | 68.627 | 70.166 | 65.036 | Player +4.9 |
| d20 | 팀 t + 내 q (ADR-3) | 69.603 | 70.162 | 68.299 | Player 비트 동일·Pitch +0.044 |
| d22 | + 볼카운트 행 항 (ADR-4) | 69.886 | 70.103 | 69.380 | **Player +1.08**, 당시 팀 최고 |
| d28 | L236 + 소이력 직교 prior | 70.111 | 70.124 | 70.081 | Player −0.48 (실패) |
| d30b | O57 + 타자 질 + drift | 69.894 | 70.114 | 69.380 | Player −1.34 (실패) |
| FIN_G(종민) | TS + r13 목표 | 70.307 | 70.094 | 70.804 | 팀 목표값 최종 |
| **dFING2** | FIN_G t + q 앙상블·T .9 (ADR-6) | **70.314** | 70.104 | **70.804** | **최종·팀 최고** |

**해석.** 내 제출 전부에서 Pitch 는 70.09~70.21(폭 0.12) 안에 갇혀 있고, Player 는 60.2 → 70.8(폭 10.6) 을 움직였다. §1 의 진단 그대로 **점수는 Player 에서 났고, Pitch 는 잃지만 않으면 됐다.** 팀 계보로 보면 Player 상승분은 F 체제 보정 γ_F +2.61 → 볼카운트 행 항 +1.08 → 직교 잔차 +0.47 → 플래툰 +0.28 → 조건부 표 r12/r13 +0.09 순이고, 내 마지막 기여(q 앙상블)는 Pitch +0.010 = Score +0.007 — 작지만 **하방 위험이 0 인 유일한 개선**이었다.

### 4-2. 속도·메모리·비용

| 항목 | 측정값 | 제한 |
|---|---|---|
| 추론 (218,836행 실물 크기 가짜 test) | **32~38초**, 최대 RSS **0.5~0.7GB** | 10분 · 28GB |
| 제출물 크기 | 40.4MB (LightGBM txt 10개 + 표 npz) | — |
| 학습 (LightGBM 5시드 × ~650 rounds, 12스레드) | 257초 | — |
| 빌드 → 게이트 → zip 한 사이클 | ~5분 (학습 데이터 캐시 700MB 재사용) | 제출 100회/일 |

추론 여유가 제한 대비 15배 이상이라 **경량화(시드 축소·피처 축소)는 검토 대상에서 뺐다** — 정확도를 내줄 이유가 없었다. 대신 채점 서버와 같은 py3.11 venv 에서 더미 실행을 매 제출 전 강제해 "설치·실행 오류로 제출 횟수를 잃는" 비용을 0 으로 유지했다.

### 4-3. 오차 분석 — 어디서 틀리는가

- **클래스 수준.** Shadow 는 투수 간 해간 지속성 0.34, 참 분산 ≈ 0 — 사실상 상수 18.5% 다. 투수 "실력"은 Heart ↔ Failure 배분에만 있다. 그래서 순위 신호는 2-class 문제로 설계하고, Shadow 확률은 q(상황)에 맡겼다. Brier 이득도 이력 500구+ 투수 행(71%)에서만 나고 신인 행(19.5%)은 0 이었다.
- **투수 군 수준(as-of 2024, 팀 감사).** 전체 τ 0.42 이지만 군별로 보면 이력 0 투수 +0.435, 3,000구+ +0.374 로 양호한 반면 **1~300구 −0.048, F 관여 투수 147명(46%) 군내 τ 0.05~0.08 = 무작위.** "전체 순위는 맞는데 절반의 투수는 순위가 안 매겨진다"가 실제 병목이었고, 여기를 겨냥한 개입(소이력 prior·F 재라벨·F×이력 크기)은 양쪽 부호 모두 LB 에서 −0.5~−7 이었다. 원인: 이 군은 2025 로 지속되는 성분(sd ≈ 0.9)이 시즌 내 분산(2.39)보다 훨씬 작아 **무엇을 학습해도 잡음**이다.
- **구조 비용.** anchor 는 행마다 t 를 강제해 행 수준 상황 정보를 지우므로 Pitch −0.14 를 낸다. 이를 복원하려는 시도(TQ·drift-anchor·ncut·cw)는 Player −0.5~−1.7 로 전부 실패 → Pitch 회수는 q 개선(앙상블·온도)만 안전하다는 결론이 ADR-6 으로 이어졌다.

### 4-4. 실패한 실험에서 배운 것

| 실험 | 오프라인 | LB | 배운 것 |
|---|---|---|---|
| 위치 이력·빗나간 크기 주입 (d6/d7) | 3폴드 3/3 ✓ | −0.05 / −0.17 | **폴드는 Player 를 못 맞춘다** → ADR-5 |
| skill prior·soft 재라벨 (d10/d14/d36e) | τ +.06~.10 | 계열 7연패, d36e −0.045 | 폴드 이득은 "F 소이력 투수 과대예측"의 거울상 |
| 소이력 직교 prior (d28) | 인샘플 +0.40 | Player −0.48 | 소이력 군 겨냥 개입은 양방향 사망 |
| 타자 질·drift-anchor (d30b) | as-of +1.28 | Player −1.34 | as-of 패널도 Player 예측력 0 |

공통 원리 하나: **"이력 측정을 정밀하게 하는 것"은 전부 실패했고, "평가 행 환경(체제·카운트·손·팀)에 대한 보정 + 강한 수축"만 통했다.** 이 대회는 실력 추정이 아니라 2025 체제 예측이었다.

## 5. 한계와 개선 — 운영 리스크와 다음 단계

**한계.**
- 2025 체제(전 구장 ABS 첫 해)를 오프라인에서 관측할 수 없어 Player 검증이 LB 에 의존했다. 100회 안팎의 LB 판정에는 선택 편향이 있고, Public = Private 라 최종 점수도 그 편향을 포함한다.
- F 관여·소이력 투수 147명의 군내 순위(τ 0.05)가 남은 병목. 여기서 τ 0.25 를 만들면 Player +2 지만 29열 밖의 정보가 없다.
- 볼카운트 행 항은 규정 문구상 합법이나 "지표를 겨냥한 보정"이라는 해석 여지가 있어 발표·코드 검증 시 설명 부담이 있다.

**운영 리스크와 대응.**
- 학습/추론 경로 불일치(팀 L8, τ −0.08) → `make_bundle()` 단일화 + 학습 스크립트 안에서 29열 가짜 test 재현 게이트.
- 채점 환경 불일치 → pickle 금지, py3.11 venv 더미 실행을 제출 전 강제.
- τ_b 동일값 착시(다른 제출이 10자리까지 같은 Player) → τ_b 는 정수 C−D 라 우연 일치가 흔함. 버그로 오판해 시간을 잃지 말 것.
- 병행 작업이 같은 `submit_dN` 을 덮어써 d11 소실 → 빌드 직전 번호 확인·접미사 명명. ssh 끊김으로 빌드가 함께 죽음 → `setsid nohup` + 완료 마커 폴링.

**다음에 다시 한다면.**
1. **첫날부터 검증 설계를 배포 시점 기준으로** — pitcher-season as-of 패널을 만들고, 이미 있는 목표값의 **잔차**를 목표로 한 순위모델(lambdarank)을 Player 라인으로 둔다. 이번엔 이 축(RK, +0.24)이 둘째 날 새벽에야 들어갔다.
2. **두 라인을 처음부터 병행** — Player 는 LB 이웃 규칙으로 탐침, Pitch 는 t 고정 q-only 로 안전하게 축적. 마지막 4시간에 찾은 ADR-6 을 첫 6시간에 세팅했으면 Pitch 폭 0.1 을 더 쓸 수 있었다.
3. **실험 대장을 한 줄 형식(가설 · 오프라인 · LB · 판정)으로 첫 시간부터 강제** — 이번엔 팀 170여 건의 제출을 가설 기준으로 되짚는 전수 감사를 둘째 날 새벽에 따로 해야 했다.
